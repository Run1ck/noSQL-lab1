## 1. Что такое Firestore

**Cloud Firestore** — документоориентированная NoSQL-база данных от Google. Она
входит в Firebase (платформа для мобильной и веб-разработки) и одновременно
является сервисом Google Cloud. Firebase-проект и Google Cloud-проект — это одно и то же.

Ключевые свойства:

- **Документная модель.** Данные хранятся как документы (набор полей, похожий на
  JSON), документы лежат в коллекциях. Жёсткой схемы нет.
- **Serverless и managed.** Сервер не нужно ни ставить, ни настраивать, ни
  масштабировать. Google сам реплицирует данные, делает шардирование и бэкапы
  инфраструктуры. Под капотом работает Spanner.
- **Строгая консистентность.** Чтение сразу видит последнюю запись, запросы тоже.
- **ACID-транзакции** с уровнем изоляции serializable, в том числе по нескольким документам.
- **Каждый запрос идёт по индексу.** Время запроса зависит от размера результата,
  а не от размера коллекции. Обратная сторона: запрос, под который нет индекса,
  просто не выполнится.
- **Realtime.** Клиент может подписаться на документ или запрос и получать
  изменения в реальном времени.
- **Оффлайн-режим** в мобильных и веб-SDK: локальный кэш и синхронизация после
  восстановления сети.
- **Security Rules.** Декларативные правила доступа, которые позволяют мобильному
  и веб-клиенту ходить в базу напрямую, без своего бэкенда.

Режимы и редакции:

- **Native mode** — классический Firestore, всё, что описано в этом файле, про него.
- **Datastore mode** — режим совместимости со старым Cloud Datastore (другой API, без realtime и Rules).
- Кроме стандартной редакции есть **Enterprise-редакция** (с совместимостью с
  MongoDB API и другим движком запросов). К лабе это не относится.

Предшественник Firestore у Firebase — **Realtime Database** (одно большое JSON-дерево).
Firestore пришёл ему на смену: нормальные запросы, коллекции, масштабирование.

## 2. Для чего применяется и для чего нет

Хорошо подходит:

- бэкенд мобильных и веб-приложений, особенно когда клиент ходит в базу напрямую;
- realtime-сценарии: чаты, ленты, совместное редактирование, статусы заказов и заявок;
- каталоги, профили пользователей, настройки, контент;
- данные с разной структурой у разных записей (schemaless);
- проекты, где не хочется администрировать базу и нужен автоскейлинг;
- прототипы и стартапы: есть бесплатный тариф.

Плохо подходит:

- **сложная аналитика и отчёты.** Нет `JOIN`, нет `GROUP BY`, есть только простые
  агрегаты `count`/`sum`/`avg`. Аналитику либо считают заранее (денормализованные
  проекции, см. раздел 10), либо выгружают в BigQuery;
- **полнотекстовый поиск.** Нет `LIKE` и морфологии, только поиск по префиксу.
  Для полноценного поиска подключают Algolia, Typesense или Elastic;
- **очень частые записи в один документ.** Рекомендуемый устойчивый темп —
  около 1 записи в секунду в один документ;
- **строгая реляционная целостность.** Нет внешних ключей, каскадов и `UNIQUE`-ограничений;
- случаи, где критичны vendor lock-in и предсказуемость счёта: оплата идёт за каждую операцию.

## 3. Модель данных

### 3.1. Документ

Документ — минимальная единица хранения. Это набор пар «поле — значение»
плюс уникальный ID внутри коллекции.

```text
requests/Xk3f9QaZ2mB7LpRt
{
  userId:    "6f1c...e2",
  createdAt: 2026-10-18T12:30:00Z,
  status: {
    code:      "new",
    changedAt: 2026-10-18T12:30:00Z
  },
  items: [
    { serviceId: "room-101", serviceName: "Аудитория 101", date: 2026-10-20 }
  ],
  details: {
    participants: 25,
    needsProjector: true,
    purpose: "семинар"
  }
}
```

- Документ читается и пишется **целиком** (можно обновить отдельные поля, но
  прочитать отдельное поле нельзя: всегда приходит весь документ).
- Максимальный размер документа — **1 MiB**.
- Документы в одной коллекции **не обязаны** иметь одинаковые поля.

### 3.2. Коллекции и подколлекции

- **Коллекция** — контейнер документов. Её не нужно создавать заранее: она
  появляется при записи первого документа и исчезает, когда в ней не осталось документов.
- Коллекция содержит только документы. Поля «на уровне коллекции» не бывает.
- **Подколлекция** — коллекция, привязанная к конкретному документу.

Путь всегда чередует коллекцию и документ:

```text
requests                                   коллекция
requests/Xk3f9QaZ2mB7LpRt                  документ
requests/Xk3f9QaZ2mB7LpRt/history          подколлекция
requests/Xk3f9QaZ2mB7LpRt/history/h1       документ в подколлекции
```

Важно: **удаление документа не удаляет его подколлекции.** Они остаются
«сиротами», их надо удалять отдельно.

**Collection group query** — запрос сразу по всем подколлекциям с одинаковым
именем, например по всем `history` всех заявок.

### 3.3. Типы данных

| Тип       | Пример                 | Комментарий                                      |
| --------- | ---------------------- | ------------------------------------------------ |
| string    | `"approved"`           | UTF-8                                            |
| integer   | `42`                   | int64                                            |
| double    | `3.14`                 | float64                                          |
| boolean   | `true`                 |                                                  |
| null      | `null`                 |                                                  |
| timestamp | `2026-10-18T12:30:00Z` | точность до микросекунд, в Go это `time.Time`    |
| map       | `{ code: "new", ... }` | вложенный объект, глубина до 20 уровней          |
| array     | `["a", "b"]`           | массив не может напрямую содержать другой массив |
| reference | `services/room-101`    | ссылка на другой документ                        |
| geopoint  | `(55.75, 37.61)`       |                                                  |
| bytes     |                        | бинарные данные                                  |
| vector    |                        | эмбеддинги для векторного поиска                 |

### 3.4. ID документов

- Можно задать свой ID (`Doc("room-101")`) или получить случайный 20-символьный
  (`NewDoc()` / `Add()`).
- **Автоинкремента нет.** Это важно для нас: в первой лабе `Request.ID` — это
  `int64` из Postgres. В Firestore придётся либо перейти на строковые ID, либо
  держать документ-счётчик и увеличивать его в транзакции (а это узкое место,
  см. лимит на запись в один документ).
- Монотонно растущие ID (`1, 2, 3...` или timestamp) при высокой нагрузке
  создают «горячую точку» в индексе. Случайные ID этого избегают.
- Свой осмысленный ID полезен, когда нужна уникальность: например,
  `bookings/room-101_2026-10-20` + `Create()` гарантирует, что одну аудиторию
  на одну дату нельзя забронировать дважды (второй `Create` упадёт с `AlreadyExists`).

### 3.5. Главные лимиты

| Что                                    | Лимит                 |
| -------------------------------------- | --------------------- |
| Размер документа                       | 1 MiB                 |
| Глубина вложенности map/array          | 20                    |
| Длина ID документа                     | до 1500 байт, без `/` |
| Устойчивый темп записи в один документ | около 1 в секунду     |
| Значений в `in` / `array-contains-any` | до 30                 |
| Индексных записей на документ          | 40 000                |
| Время жизни транзакции                 | 270 секунд            |

## 4. Сравнение с Redis и Postgres

|                 | Redis (лаба 1)             | Postgres (лаба 1)           | Firestore (лаба 2)                                      |
| --------------- | -------------------------- | --------------------------- | ------------------------------------------------------- |
| Модель          | ключ — значение, в памяти  | таблицы и строки            | коллекции и документы                                   |
| Схема           | нет                        | строгая (DDL)               | нет                                                     |
| Связи           | вручную                    | внешние ключи, `JOIN`       | денормализация или ссылки, без `JOIN`                   |
| Запросы         | по ключу, структуры данных | любой SQL                   | фильтры и сортировка только по индексам                 |
| Агрегации       | вручную                    | `GROUP BY`, оконные функции | только `count`/`sum`/`avg`                              |
| Транзакции      | `MULTI`, Lua               | ACID                        | ACID, serializable                                      |
| TTL             | встроенный                 | нет                         | есть TTL-политики (удаление в течение суток, не точное) |
| Масштабирование | вручную, кластер           | вручную, реплики            | автоматически                                           |
| Развёртывание   | свой сервер или Docker     | свой сервер или Docker      | облако Google или локальный эмулятор                    |
| Оплата          | ресурсы сервера            | ресурсы сервера             | каждое чтение, запись и удаление                        |

Главный сдвиг в мышлении при переходе с SQL: **в SQL проектируют под данные, а
в Firestore под запросы.** Сначала выписывают, какие запросы будет делать
приложение, потом раскладывают данные так, чтобы каждый запрос был простым
чтением одного документа или одним запросом по одной коллекции.

## 5. Как проектировать данные

### 5.1. Три способа хранить связанные данные

**1. Вложить в документ (map или array).**

```text
requests/{id} { ..., details: { participants: 25, needsProjector: true } }
```

- плюсы: читается одним запросом, обновляется атомарно вместе с документом;
- минусы: растёт размер документа (лимит 1 MiB), документ читается целиком;
- подходит для небольших данных, которые всегда нужны вместе с родителем:
  характеристики, адрес, текущий статус.

**2. Подколлекция.**

```text
requests/{id}/history/{changeId} { from: "new", to: "approved", at: ..., by: ... }
```

- плюсы: неограниченный объём, можно запрашивать отдельно, есть collection group query;
- минусы: отдельное чтение;
- подходит для того, что растёт без ограничений: история, комментарии, логи.

**3. Отдельная корневая коллекция + ссылка по ID.**

```text
services/room-101            { name: "Аудитория 101", kind: "room", active: true }
requests/{id}                { items: [{ serviceId: "room-101", ... }] }
```

- плюсы: одна сущность хранится в одном месте, её можно запрашивать саму по себе;
- минусы: чтобы показать название, нужен второй запрос (`JOIN` нет);
- подходит для самостоятельных сущностей и **справочников**.

### 5.2. Денормализация

Чтобы не делать N дополнительных запросов, часть данных **копируют** в
документ, который их показывает. Например, кладут `serviceName` прямо в элемент
заявки рядом с `serviceId`.

Цена денормализации: при изменении оригинала нужно обновить все копии. Делают
это транзакцией или пакетом, чтобы копии не разъехались. Ровно это и
проверяет требование 4 лабы: «транзакционно или пакетно изменять связанную
сущность и вложенные данные».

### 5.3. Массивы объектов и запросы

Firestore **не умеет** фильтровать по полю объекта внутри массива. Запрос
«все заявки, где `items[].serviceId == "room-101"`» не написать. Оператор
`array-contains` сравнивает элемент массива целиком.

Обходной путь — продублировать нужные значения в плоский массив:

```text
items:      [{ serviceId: "room-101", date: ... }, { serviceId: "lab-3", date: ... }]
serviceIds: ["room-101", "lab-3"]
```

Тогда работает `where("serviceIds", "array-contains", "room-101")`.

## 6. Индексы

Каждый запрос в Firestore обслуживается индексом. Индексов два вида.

### 6.1. Одиночные индексы (single-field)

Создаются **автоматически** для каждого поля документа, включая подполя map
(`status.code`, `details.participants`): по возрастанию, по убыванию и для
`array-contains` по массивам. Их хватает для запросов вида:

- равенство или диапазон по одному полю: `where createdAt >= X`;
- сортировка по одному полю: `orderBy createdAt desc`;
- несколько равенств по разным полям: Firestore умеет склеивать одиночные индексы.

Ненужные поля можно исключить из автоиндексации (exemption): например, длинный
текст или поле, которое пишется очень часто. Это экономит место и ускоряет запись.

### 6.2. Составные индексы (composite)

Индекс по нескольким полям сразу. **Автоматически не создаётся**, его нужно
описать явно. Он нужен, когда запрос сочетает условия по разным полям, например:

- равенство по одному полю + сортировка по другому;
- равенство по одному полю + диапазон по другому;
- диапазоны или неравенства по нескольким полям.

Запрос из нашего задания, «поиск по состоянию и дате создания», как раз такой:

```text
where status.code == "new"
  and createdAt >= 2026-10-01
orderBy createdAt desc
```

Без составного индекса `(status.code ASC, createdAt DESC)` реальный Firestore
вернёт ошибку:

```text
rpc error: code = FailedPrecondition desc = The query requires an index.
You can create it here: https://console.firebase.google.com/v1/r/project/.../firestore/indexes?create_composite=...
```

В ошибке есть готовая ссылка, по которой индекс создаётся в один клик. Это и
есть способ «продемонстрировать необходимость» индекса (требование 6): показать
запрос и ошибку до создания индекса, потом создать индекс, дождаться статуса
`READY` и показать, что запрос заработал.

### 6.3. Как описывать индексы

Индексы хранят в репозитории в файле `firestore.indexes.json` и деплоят через Firebase CLI:

```json
{
  "indexes": [
    {
      "collectionGroup": "requests",
      "queryScope": "COLLECTION",
      "fields": [
        { "fieldPath": "status.code", "order": "ASCENDING" },
        { "fieldPath": "createdAt", "order": "DESCENDING" }
      ]
    }
  ],
  "fieldOverrides": []
}
```

```bash
firebase deploy --only firestore:indexes
```

То же самое через gcloud:

```bash
gcloud firestore indexes composite create \
  --collection-group=requests \
  --field-config=field-path=status.code,order=ascending \
  --field-config=field-path=createdAt,order=descending
```

Индекс строится не мгновенно: на непустой коллекции это может занять минуты.

### 6.4. Важно: эмулятор не проверяет индексы

Локальный эмулятор Firestore **не отслеживает составные индексы и выполняет
любой корректный запрос**. На эмуляторе ошибки `requires an index` не будет.
Поэтому для демонстрации требования 6 нужен настоящий Firebase-проект
(бесплатного тарифа Spark достаточно).

### 6.5. Query Explain

У Firestore есть Query Explain: он показывает, какой индекс использовался,
сколько индексных записей просмотрено и сколько документов прочитано. В Go это
`query.WithRunOptions(firestore.ExplainOptions{Analyze: true})`. Им удобно
подкрепить демонстрацию индекса цифрами.

### 6.6. Связь с миграцией

Требование 7 превращает строковый `status` во вложенный объект. Значит, поле в
индексе меняется со `status` на `status.code`. Индекс под новое поле нужен
заранее, а запросы во время миграции должны учитывать оба формата (см. раздел 12).

## 7. Запросы

### 7.1. Операторы фильтрации

| Оператор             | Смысл                                             |
| -------------------- | ------------------------------------------------- |
| `==`, `!=`           | равно, не равно                                   |
| `<`, `<=`, `>`, `>=` | диапазон (работает и для строк, и для timestamp)  |
| `in`                 | значение из списка (до 30)                        |
| `not-in`             | значение не из списка                             |
| `array-contains`     | массив содержит элемент                           |
| `array-contains-any` | массив содержит хотя бы один из элементов (до 30) |

Условия по умолчанию объединяются через AND. OR тоже есть (`OrFilter`).

**Документы без поля в выборку не попадают**: ни при фильтре по этому полю,
ни при сортировке по нему. `!=` и `not-in` тоже не возвращают документы, где
поля нет. Это легко забыть при миграциях.

### 7.2. Фильтры по вложенным полям

Вложенные поля адресуются через точку. Отдельно ничего настраивать не нужно,
одиночные индексы на подполя map создаются автоматически:

```go
q := client.Collection("requests").
	Where("details.participants", ">=", 30).
	Where("details.needsProjector", "==", true)
```

Это закрывает требование 3 «поиск по вложенным полям».

### 7.3. Сортировка и лимит

```go
q := client.Collection("requests").
	OrderBy("createdAt", firestore.Desc).
	Limit(20)
```

Последним неявным критерием сортировки всегда идёт ID документа (`__name__`),
поэтому порядок детерминирован.

### 7.4. Пагинация

Есть два способа.

**Курсоры — правильный способ.** Запоминают позицию последнего документа страницы
и начинают следующую страницу после него:

```go
q := client.Collection("requests").
	Where("status.code", "==", "new").
	OrderBy("createdAt", firestore.Desc).
	Limit(20)

next := q.StartAfter(lastSnap)
```

Курсор задаётся снапшотом последнего документа или значениями полей сортировки:
`q.StartAfter(lastCreatedAt)`. Есть `StartAt`, `StartAfter`, `EndAt`,
`EndBefore`. Для REST API курсор обычно кодируют в непрозрачный токен
(например, base64 от `createdAt` и ID) и отдают клиенту как `nextPageToken`.

**Offset — плохой способ.** `Offset(100)` существует, но пропущенные документы
всё равно читаются и **оплачиваются**, а на больших смещениях это медленно.

### 7.5. Поиск по строкам

`LIKE` и полнотекстового поиска нет. Работает только поиск по префиксу через диапазон:

```go
q := client.Collection("services").
	Where("name", ">=", prefix).
	Where("name", "<=", prefix+"").
	OrderBy("name", firestore.Asc)
```

Регистр учитывается, поэтому обычно хранят дополнительное поле `nameLower`.

### 7.6. Агрегации

```go
res, err := client.Collection("requests").
	Where("status.code", "==", "new").
	NewAggregationQuery().
	WithCount("total").
	Get(ctx)

total := res["total"].(*firestorepb.Value).GetIntegerValue()
```

Есть `WithCount`, `WithSum`, `WithAvg`. Агрегация оплачивается примерно как
1 чтение на каждые 1000 просмотренных индексных записей.

**`GROUP BY` нет.** Запрос «сколько изменений было по каждому часу» одним
запросом не сделать. Поэтому в задании и требуется денормализованная проекция
(раздел 10).

### 7.7. Чего в запросах нет

- `JOIN` — данные из двух коллекций читаются двумя запросами;
- `GROUP BY`, `HAVING`, оконные функции;
- `LIKE`, регулярные выражения, полнотекстовый поиск;
- фильтры по полям объектов внутри массива;
- запросы, под которые нет индекса.

### 7.8. Realtime-подписки

Вместо разового `Documents(ctx)` можно вызвать `Snapshots(ctx)` и получать
новые версии документа или результата запроса при каждом изменении. Для лабы
это не обязательно, но это одна из главных фич Firestore.

## 8. Запись данных

### 8.1. Операции

| Операция                          | Если документа нет      | Если документ есть                 |
| --------------------------------- | ----------------------- | ---------------------------------- |
| `Create(data)`                    | создаёт                 | ошибка `AlreadyExists`             |
| `Set(data)`                       | создаёт                 | **полностью перезаписывает**       |
| `Set(data, firestore.MergeAll)`   | создаёт                 | сливает поля, остальные не трогает |
| `Update([]firestore.Update{...})` | ошибка `NotFound`       | меняет только указанные поля       |
| `Delete()`                        | ничего                  | удаляет (подколлекции остаются)    |
| `Collection.Add(data)`            | создаёт со случайным ID | —                                  |

`Update` принимает пути через точку, поэтому можно поменять одно вложенное поле,
не трогая остальные:

```go
_, err := ref.Update(ctx, []firestore.Update{
	{Path: "status.code", Value: "approved"},
	{Path: "status.changedAt", Value: firestore.ServerTimestamp},
})
```

А вот `{Path: "status", Value: map[string]any{...}}` заменит объект `status` целиком.

### 8.2. Специальные значения

| Значение                      | Что делает                                       |
| ----------------------------- | ------------------------------------------------ |
| `firestore.ServerTimestamp`   | подставляет время сервера в момент записи        |
| `firestore.Increment(n)`      | атомарно прибавляет `n` к числу (без чтения)     |
| `firestore.ArrayUnion(v...)`  | добавляет в массив элементы, которых там ещё нет |
| `firestore.ArrayRemove(v...)` | удаляет элементы из массива                      |
| `firestore.Delete`            | удаляет поле из документа                        |

`Increment` особенно важен для счётчиков и проекций: ему не нужно сначала
читать документ, и он не теряет обновления при конкурентной записи.

## 9. Транзакции и пакетная запись

### 9.1. Транзакции

Транзакция — набор чтений и записей, который выполняется атомарно и изолированно.

```go
err := client.RunTransaction(ctx, func(ctx context.Context, tx *firestore.Transaction) error {
	snap, err := tx.Get(ref)
	if err != nil {
		return err
	}
	code, err := snap.DataAt("status.code")
	if err != nil {
		return err
	}
	if code != "new" {
		return ErrAlreadyProcessed
	}
	return tx.Update(ref, []firestore.Update{
		{Path: "status.code", Value: "approved"},
	})
})
```

Правила:

- **все чтения должны быть до всех записей** внутри транзакции;
- если функция вернула ошибку, ничего не записывается;
- при конфликте с другой транзакцией Firestore **перезапускает функцию**
  (по умолчанию до 5 попыток). Поэтому внутри функции не должно быть побочных
  эффектов: никаких HTTP-запросов, записей в Redis и изменения внешних переменных.
  Инвалидацию кэша делают **после** успешного `RunTransaction`;
- серверные SDK (Go в том числе) используют пессимистичные блокировки на
  прочитанные документы, клиентские SDK используют оптимистичную схему;
- транзакция не может жить дольше 270 секунд.

Транзакция может трогать документы из разных коллекций. Например, одним
коммитом поменять статус заявки, записать событие в историю и увеличить счётчик в проекции.

### 9.2. Пакетная запись

Пакет (batched write) — набор только записей без чтений, которые применяются
атомарно: либо все, либо ни одной.

В Go-SDK старый `client.Batch()` (`WriteBatch`) помечен как устаревший. Вместо него:

- **`RunTransaction`**, если нужна атомарность;
- **`BulkWriter`**, если нужна скорость массовой записи (например, для миграции),
  но атомарность не нужна: каждая операция применяется отдельно, параллельно и с
  автоматическим ограничением темпа.

```go
bw := client.BulkWriter(ctx)
for _, s := range services {
	if _, err := bw.Set(client.Collection("services").Doc(s.ID), s); err != nil {
		return err
	}
}
bw.End()
```

## 10. Денормализованные проекции и счётчики

**Проекция** — отдельная коллекция с заранее посчитанными данными под
конкретный запрос. Она обновляется **в той же транзакции**, что и исходные
данные, поэтому не может разойтись с ними.

Наш случай: «количество изменений по временным интервалам». Каждое изменение
заявки (создание, одобрение, отклонение, отмена) увеличивает счётчик в
документе своего интервала:

```text
change_stats_hourly/2026-10-18T14
{
  bucketStart: 2026-10-18T14:00:00Z,
  total: 17,
  byStatus: { new: 9, approved: 5, rejected: 2, cancelled: 1 }
}
```

Обновление внутри транзакции изменения заявки:

```go
now := time.Now().UTC()
statRef := client.Collection("change_stats_hourly").Doc(now.Format("2006-01-02T15"))

err := tx.Set(statRef, map[string]any{
	"bucketStart": now.Truncate(time.Hour),
	"total":       firestore.Increment(1),
	"byStatus":    map[string]any{"approved": firestore.Increment(1)},
}, firestore.MergeAll)
```

Чтение аналитики — обычный запрос по диапазону:

```go
q := client.Collection("change_stats_hourly").
	Where("bucketStart", ">=", from).
	Where("bucketStart", "<", to).
	OrderBy("bucketStart", firestore.Asc)
```

Интервалы можно вести сразу на нескольких уровнях (час, день) в разных
коллекциях или документах. Это несколько `Increment` в одной транзакции.

**Распределённые счётчики.** Если в один документ-счётчик пишут чаще примерно
раза в секунду, начинаются конфликты. Тогда счётчик дробят на N шардов
(`.../shards/0..N-1`), пишут в случайный шард, а при чтении суммируют. Для
нагрузки лабы это не нужно, но знать о такой технике стоит.

## 11. Security Rules

### 11.1. Что это и на кого действует

Security Rules — декларативные правила доступа к документам. Они проверяются на
стороне Firestore при каждом запросе.

**Важно:** правила действуют **только** на клиентские SDK (Web, Android, iOS) и
на REST/RPC-запросы с токеном Firebase Auth. **Серверные библиотеки, включая
Go-клиент `cloud.google.com/go/firestore`, авторизуются через IAM (сервисный
аккаунт) и правила игнорируют.** Поэтому наш Go-бэкенд правила не ограничивают:
проверять их нужно отдельно, через эмулятор и тесты.

### 11.2. Синтаксис

```text
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn() {
      return request.auth != null;
    }

    function isAdmin() {
      return signedIn() && request.auth.token.role == 'admin';
    }

    match /requests/{requestId} {
      allow read: if isAdmin()
                  || (signedIn() && resource.data.userId == request.auth.uid);

      allow create: if signedIn()
                    && request.resource.data.userId == request.auth.uid
                    && request.resource.data.status.code == 'new';

      allow update: if isAdmin()
                    && request.resource.data.diff(resource.data).affectedKeys()
                         .hasOnly(['status', 'updatedAt']);

      allow delete: if false;
    }

    match /service_kinds/{kindId} {
      allow read: if true;
      allow write: if isAdmin();
    }

    match /change_stats_hourly/{bucket} {
      allow read: if isAdmin();
      allow write: if false;
    }
  }
}
```

Что тут есть:

- `match` — к каким путям относится правило; `{requestId}` — переменная,
  `{doc=**}` — все вложенные пути;
- `allow <операция>: if <условие>`. Операции: `read` = `get` + `list`,
  `write` = `create` + `update` + `delete`;
- `request.auth` — кто делает запрос (`uid` и claims токена в `request.auth.token`);
- `resource.data` — документ **до** изменения;
- `request.resource.data` — документ **после** изменения (то, что пытаются записать);
- `get(path)` и `exists(path)` — прочитать другой документ прямо в правиле
  (например, проверить роль в `users/{uid}`). Каждый такой вызов оплачивается как чтение;
- по умолчанию всё запрещено: если ни одно правило не разрешило, запрос отклоняется.

**Правила — не фильтры.** Если клиент делает запрос по коллекции, Firestore не
отбрасывает «чужие» документы молча. Он отклоняет запрос целиком, если не может
доказать, что все результаты разрешены. Поэтому клиент должен сам добавлять
условие, например `where userId == myUid`.

### 11.3. Своя авторизация и Rules

В первой лабе своя JWT-авторизация, а Rules понимают только токены Firebase Auth.
Связать их можно так: бэкенд через Firebase Admin SDK для Go
(`firebase.google.com/go/v4/auth`) выпускает custom token с claim
`role: "admin"`, клиент обменивает его на Firebase-токен (`signInWithCustomToken`),
а в правилах это становится доступно как `request.auth.token.role`.

### 11.4. Деплой и тестирование

```bash
firebase deploy --only firestore:rules
```

Тестируют правила на эмуляторе. Официальный способ — библиотека
`@firebase/rules-unit-testing` (JavaScript): создаёшь контексты разных
пользователей (`authenticatedContext('u1', { role: 'admin' })`,
`unauthenticatedContext()`) и проверяешь операции через `assertSucceeds` /
`assertFails`. В консоли реального проекта есть Rules Playground для ручной проверки.

## 12. Миграции схемы

### 12.1. Особенности миграций в schemaless-базе

`ALTER TABLE` здесь нет. Схема живёт в коде, а данные в разных документах могут
быть в разных форматах одновременно. Миграция — это программа, которая проходит
по документам и переписывает их.

Требование задания — **повторяемая** миграция: её можно запустить сколько угодно
раз, и результат будет тот же (идемпотентность).

### 12.2. Наш случай: строковый статус → вложенный объект

```text
было:  status: "approved"
стало: status: { code: "approved", changedAt: ..., changedBy: "...", comment: "..." }
```

Приёмы, которые делают миграцию повторяемой и безопасной:

1. **Проверять текущий формат перед записью.** Если `status` уже map — пропустить
   документ. Если строка — преобразовать.
2. **Хранить версию схемы** в документе (`schemaVersion: 2`).
3. **Проверку и запись делать в одной транзакции**, чтобы не затереть изменение,
   которое приложение сделало между чтением и записью.
4. **Проходить коллекцию страницами** по ID документа (`OrderBy(firestore.DocumentID, firestore.Asc)` + `StartAfter`).
5. **Не искать неотмигрированные запросом** вида `where schemaVersion < 2`:
   документы, где поля `schemaVersion` нет вообще, такой запрос не вернёт
   (см. 7.1). Проверять нужно в коде.
6. Записать факт и результат прогона в служебный документ, например
   `_migrations/status_to_object { appliedAt, migrated, skipped }`.

Набросок:

```go
err := client.RunTransaction(ctx, func(ctx context.Context, tx *firestore.Transaction) error {
	snap, err := tx.Get(ref)
	if err != nil {
		return err
	}
	raw, err := snap.DataAt("status")
	if err != nil {
		return err
	}
	code, ok := raw.(string)
	if !ok {
		return nil
	}
	return tx.Update(ref, []firestore.Update{
		{Path: "status", Value: map[string]any{"code": code, "changedAt": snap.UpdateTime}},
		{Path: "schemaVersion", Value: 2},
	})
})
```

### 12.3. Код приложения во время миграции

Пока миграция не прошла по всем документам, в базе лежат оба формата. Если Go
читает документ через `DataTo` в структуру, где `Status` — это struct, на
строковом статусе декодирование упадёт. Варианты:

- читать `snap.Data()` в `map[string]any` и разбирать `status` через type switch;
- или сначала прогнать миграцию, а потом выкатывать код с новым форматом.

Классический подход — **expand/contract**: код сначала учится читать оба формата,
потом проходит миграция, потом поддержку старого формата удаляют.

## 13. Кэширование Firestore через Redis

Зачем кэшировать Firestore, если он и так быстрый:

- каждое чтение **стоит денег**, а пустой результат запроса тоже оплачивается как 1 чтение;
- Redis отвечает быстрее сетевого запроса в облако;
- одинаковые запросы (список заявок со статусом `new`, справочники) повторяются часто.

Схема **cache-aside**, та же, что в первой лабе для услуг:

1. сформировать ключ из параметров запроса: `fs:requests:v{ver}:{hash(фильтр, сортировка, курсор)}`;
2. `GET` в Redis: есть значение — вернуть его;
3. нет — сходить в Firestore, положить результат через `SET ... EX <ttl>`, вернуть.

**Инвалидация** при изменении данных. Варианты:

- удалить конкретные ключи (`DEL`), если их можно вычислить;
- **версионирование пространства ключей**: хранить `fs:requests:ver` и делать
  `INCR` при каждой записи. Новые запросы строят ключи с новой версией, а старые
  ключи никто больше не читает, и они сами умирают по TTL. Не нужен `SCAN` по шаблону;
- TTL — страховка: даже если инвалидация не сработала, устаревшие данные проживут не дольше TTL.

Инвалидацию делают **после** успешного коммита транзакции в Firestore, а не
внутри функции транзакции: она может быть перезапущена или откатиться.

## 14. Работа из Go

### 14.1. Библиотеки

```bash
go get cloud.google.com/go/firestore
```

| Пакет                                                           | Зачем                                                                              |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `cloud.google.com/go/firestore`                                 | клиент Firestore                                                                   |
| `google.golang.org/api/iterator`                                | `iterator.Done` для перебора результатов                                           |
| `google.golang.org/grpc/codes`, `google.golang.org/grpc/status` | разбор ошибок (`NotFound`, `AlreadyExists`, `FailedPrecondition`)                  |
| `cloud.google.com/go/firestore/apiv1/firestorepb`               | значения в результатах агрегаций                                                   |
| `firebase.google.com/go/v4`                                     | Firebase Admin SDK, нужен только для custom tokens; для данных хватает пакета выше |

### 14.2. Подключение

```go
client, err := firestore.NewClient(ctx, projectID)
if err != nil {
	return err
}
defer client.Close()
```

- Клиент потокобезопасный. Его создают один раз при старте, как пул Postgres или клиент Redis.
- Учётные данные берутся из переменной `GOOGLE_APPLICATION_CREDENTIALS` (путь
  к JSON-ключу сервисного аккаунта).
- Если задана переменная `FIRESTORE_EMULATOR_HOST=localhost:8081`, SDK сам
  подключается к эмулятору, ключ не нужен.
- Для неосновной базы проекта есть `firestore.NewClientWithDatabase(ctx, projectID, databaseID)`.

### 14.3. Маппинг структур

```go
type requestDoc struct {
	UserID        string         `firestore:"userId"`
	Items         []itemDoc      `firestore:"items"`
	ServiceIDs    []string       `firestore:"serviceIds"`
	Status        statusDoc      `firestore:"status"`
	Details       map[string]any `firestore:"details,omitempty"`
	CreatedAt     time.Time      `firestore:"createdAt"`
	SchemaVersion int            `firestore:"schemaVersion"`
}

type itemDoc struct {
	ServiceID   string    `firestore:"serviceId"`
	ServiceName string    `firestore:"serviceName"`
	Date        time.Time `firestore:"date"`
}

type statusDoc struct {
	Code      string    `firestore:"code"`
	ChangedAt time.Time `firestore:"changedAt"`
	ChangedBy string    `firestore:"changedBy,omitempty"`
	Comment   string    `firestore:"comment,omitempty"`
}
```

Теги: `firestore:"name"` задаёт имя поля, `omitempty` не пишет нулевые значения,
`firestore:"-"` пропускает поле, `serverTimestamp` подставляет серверное время
при записи нулевого `time.Time`. ID документа в данных не хранится, его берут из `snap.Ref.ID`.

### 14.4. CRUD

```go
col := client.Collection("requests")

ref := col.NewDoc()
if _, err := ref.Create(ctx, doc); err != nil {
	return err
}

snap, err := col.Doc(id).Get(ctx)
if status.Code(err) == codes.NotFound {
	return ErrNotFound
}
if err != nil {
	return err
}
var d requestDoc
if err := snap.DataTo(&d); err != nil {
	return err
}

_, err = col.Doc(id).Update(ctx, []firestore.Update{
	{Path: "status.code", Value: "rejected"},
	{Path: "status.comment", Value: comment},
})

_, err = col.Doc(id).Delete(ctx)
```

### 14.5. Запрос с перебором результатов

```go
iter := col.
	Where("status.code", "==", "new").
	OrderBy("createdAt", firestore.Desc).
	Limit(20).
	Documents(ctx)
defer iter.Stop()

for {
	snap, err := iter.Next()
	if errors.Is(err, iterator.Done) {
		break
	}
	if err != nil {
		return err
	}
	var d requestDoc
	if err := snap.DataTo(&d); err != nil {
		return err
	}
}
```

Для небольших выборок есть `iter.GetAll()`, а для чтения нескольких документов
по известным ID — `client.GetAll(ctx, refs)`.

### 14.6. Как это встраивается в нашу архитектуру

В проекте уже есть интерфейс `request.Repository` (`internal/domain/request/repository.go`)
и его реализация на Postgres в `internal/adapter/postgres/`. Firestore естественно
ложится как ещё один адаптер, например `internal/adapter/firestore/`, который
реализует тот же интерфейс. Use case'ы и HTTP-слой при этом не меняются, что и
требуется («существующие CRUD API должны продолжать работать»). Redis-кэш можно
навесить декоратором поверх репозитория, как это уже сделано в `internal/adapter/repository/`.

## 15. Как развернуть: облако или эмулятор

### 15.1. Настоящий Firebase-проект

1. Зайти в [Firebase Console](https://console.firebase.google.com), создать проект.
2. Build → Firestore Database → Create database. Выбрать регион (например,
   `eur3` или `europe-west`). **Регион потом поменять нельзя.**
3. Выбрать стартовый режим правил: production (всё запрещено) или test
   (всё разрешено на 30 дней). Для бэкенда на Go это не важно, он ходит в обход правил.
4. Project settings → Service accounts → Generate new private key. Скачанный JSON
   и есть ключ. **Не коммитить его в git** (добавить в `.gitignore`).
5. Запускать приложение с `GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json`.

Firebase CLI для деплоя правил и индексов:

```bash
npm install -g firebase-tools
firebase login
firebase init firestore
firebase deploy --only firestore:rules,firestore:indexes
```

`firebase init firestore` создаёт `firebase.json`, `.firebaserc`, `firestore.rules` и `firestore.indexes.json`.

### 15.2. Локальный эмулятор

Эмулятор нужен для разработки и тестов без облака. Есть два варианта.

**gcloud-эмулятор в Docker** (удобно добавить в `deploy/compose.yaml`):

```yaml
firestore:
  image: gcr.io/google.com/cloudsdktool/google-cloud-cli:emulators
  command: ["gcloud", "emulators", "firestore", "start", "--host-port=0.0.0.0:8081"]
  ports:
    - "127.0.0.1:8081:8081"
```

Приложение запускается с `FIRESTORE_EMULATOR_HOST=localhost:8081`, а project ID
может быть любым (например, `demo-booking`).

**Firebase Emulator Suite** (`firebase emulators:start --only firestore`):
вдобавок веб-интерфейс для просмотра данных, загрузка `firestore.rules`,
сохранение и загрузка данных между запусками (`--import`, `--export-on-exit`).

Отличия эмулятора от продакшена, которые нам важны:

- **составные индексы не проверяются** (см. 6.4);
- данные по умолчанию живут в памяти и пропадают при перезапуске;
- поведение транзакций и лимиты реализованы не полностью.

Разумная схема для лабы: разработка и тесты на эмуляторе, а демонстрация
индекса (и, по желанию, финальный прогон) на реальном проекте с бесплатным тарифом.

### 15.3. Резервное копирование

В облаке есть экспорт и импорт базы в Cloud Storage (`gcloud firestore export`),
расписание бэкапов и PITR (восстановление на момент времени в пределах 7 дней).

## 16. Сколько это стоит

Оплата идёт за операции, хранение и исходящий трафик:

- каждый прочитанный документ — 1 чтение (в том числе каждый документ в результате запроса);
- запрос с пустым результатом — тоже 1 чтение;
- каждое срабатывание realtime-подписки — чтение изменившихся документов;
- записи и удаления считаются отдельно;
- обновление индексов при записи входит в стоимость записи.

Бесплатный тариф **Spark** (в день): 50 000 чтений, 20 000 записей, 20 000
удалений, плюс 1 GiB хранения. Для лабы этого хватает с огромным запасом.
Главное — не устроить бесконечный цикл чтений в нагрузочном тесте.

## 18. Подводные камни

- Под запрос по нескольким полям нужен составной индекс, а **эмулятор об этом молчит**.
- Документы **без поля** не попадают в выборку при фильтре или сортировке по этому полю.
- `Set` без `MergeAll` **затирает весь документ**.
- `Update` с путём `"status"` заменяет объект целиком, а с путём `"status.code"` — одно поле.
- Внутри транзакции сначала чтения, потом записи. Функция может выполниться
  несколько раз: никаких побочных эффектов.
- Удаление документа не удаляет подколлекции.
- Фильтровать по полю объекта внутри массива нельзя, нужен дублирующий плоский массив.
- `Offset` оплачивает пропущенные документы, для пагинации нужны курсоры.
- Go-бэкенд обходит Security Rules. Правила проверяются только для клиентских запросов.
- Автоинкремента нет. Счётчик ID в одном документе — узкое место (около 1 записи в секунду).
- Регион базы выбирается один раз навсегда.
- JSON-ключ сервисного аккаунта нельзя коммитить.
