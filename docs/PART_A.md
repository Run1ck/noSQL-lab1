## Решения по коду

- Соглашение: проверки вида `var _ Interface = (*T)(nil)` не пишем.
- Соглашение: у каждого Lua-скрипта в комментарии расписаны `KEYS[i]`, `ARGV[i]` и что он
  возвращает — сигнатуры у скрипта нет, связь с `Run(ctx, rdb, keys, args...)` только по позиции.

### `redisstore.New` (`internal/storage/redisstore/redis.go`)

- `PING` при создании: приложение падает на старте, а не на первом запросе.
- **Таймауты короче дефолтных go-redis:** `DialTimeout`/`ReadTimeout`/`WriteTimeout` 500 мс,
  `DialerRetries: 1`. Дефолты (5 с на подключение и ответ, 5 попыток подключения с паузой 100 мс,
  3 повтора команды) рассчитаны на далёкий сервер. Замер: при отказе Redis fail-open лимита API
  с дефолтами — **~1,7 с на каждый API-запрос** (в основном попытки подключения), с нашими —
  17–37 мс.
- `DialerRetries` — это число *попыток* подключения (1 = одна попытка), хотя go-redis называет поле
  «retry attempts»; `0` — дефолт, 5 попыток.
- **`MaxRetries: -1` — без повторов команд.** go-redis повторяет команду после таймаута чтения, а
  Redis к этому моменту её, возможно, уже выполнил: Lua-скрипт лимита выполнится дважды, одна
  заявка посчитается за две → ложный бан (ревью воспроизвело: ответ задержан на 700 мс → счётчик 2).
  С `ReadTimeout` 500 мс это реально при подвисании Redis (fork/AOF, нагрузочный тест). Мёртвые
  соединения после рестарта Redis пул отсеивает сам при выдаче, так что повторы почти ничего не дают.
- **Худший случай — Redis «завис»** (принимает соединение и молчит). Замер после исправлений:
  50 параллельных `Allow` — до 0,5 с, 1000 параллельных — до **2,0 с** (до исправлений 1,04 и
  3,17 с). Больше `PoolSize` (10 × GOMAXPROCS, на 8-ядерном Mac — 80) запросы ждут соединение из
  пула до `PoolTimeout` = `ReadTimeout` + 1 с. `PoolTimeout` не уменьшаем: под честной большой
  нагрузкой запросы начали бы получать ошибку пула и проходить без лимита.
- Дедлайн из `ctx` go-redis по умолчанию **не** применяет к чтению из сокета
  (`ContextTimeoutEnabled: false`), поэтому таймауты задаём в настройках клиента, а не через `ctx`
  (ожидание пула, подключение и паузы `ctx` при этом соблюдают).
- Под нагрузкой: 2000 параллельных `Allow` на живом Redis → ровно 60 из 60, 0 ошибок, до 93 мс.
- Тесты: `New` к закрытому порту (`127.0.0.1:1`) — ошибка быстрее 500 мс; «молчащий» сервер —
  ошибка за ~`ReadTimeout`, а не 5 с; `TestNew_NoRetryAfterReadTimeout` — прокси задерживает один
  ответ дольше `ReadTimeout`, `INCR` выполнен ровно один раз. Проверено мутацией: с `MaxRetries: 1`
  тест падает. Прокси задерживает только *один* ответ: если задерживать все, повтор застревает уже
  на рукопожатии `HELLO` нового соединения, и тест ничего не ловит.

### Корзина (`internal/storage/redisstore/cart.go`)

- Ключ `cart:{userID}`, SET из `serviceID|YYYY-MM-DD`. Разбор — по **последнему** `|`
  (в дате его нет, в ID услуги может быть).
- Пустой SET Redis удаляет сам → «корзины нет» и «корзина пуста» неразличимы; `Get` всегда
  отдаёт корзину (пустую, если ключа нет), `TTL` отдаёт 0 при `PTTL` -2/-1.
- `Save` — **перезапись** корзины: `DEL` + `SADD` + `PEXPIRE` в `MULTI/EXEC` (`TxPipelined`),
  чтобы ключ не остался без TTL. Пустая корзина → `DEL`.
- `Save` проверяет позиции (`ServiceID != ""`, `Date.IsValid()`): битая позиция не прочиталась бы
  обратно, и `Get` падал бы до конца TTL.
- `RemoveItem` — Lua (`removeItemScript`): `SREM`, и только если удалили — `PEXPIRE`. Промах → `ErrItemNotFound`,
  TTL не продлевается.
- Битая позиция в Redis → ошибка через `%v`, не `%w`: иначе `httpx.WriteError` вернёт
  400 `invalid_date` вместо 500.
- go-redis `PTTL`: для -1/-2 возвращает `time.Duration(-1/-2)` (наносекунды), не умноженные на ms.
- **Гонка при добавлении — принята.** Добавление в корзину есть только в `POST /api/cart/items`
  (`cartapi`): Get → `c.AddItem` → Save. Два параллельных добавления одного пользователя (две
  вкладки, быстрые клики в UI) могут потерять позицию: второй `Save` перезапишет корзину своим
  снимком. Лечится методом `cart.AddItem` (`SADD` + `PEXPIRE`) в контракте — решили не делать,
  для лабы не критично.

### Лимит API (`internal/ratelimit/window.go`)

- `NewRedis(rdb, prefix, limit, window)` → `*FixedWindow`; ключ `prefix:{key}`, в main — `rl:api:{ip}`.
- Фиксированное окно, Lua `windowScript`: `INCR`, затем `PTTL`; если TTL нет (`-1`) — `PEXPIRE` на
  окно. Это и первый запрос окна, и «лечение» счётчика без TTL (иначе IP заблокирован навсегда и
  ключ не вытесняется под `volatile-lru`). Скрипт отдаёт `{n, ttl}`, решение принимает Go:
  `Allowed = n <= limit`, `Remaining = max(0, limit-n)`, при отказе `RetryAfter = ttl`, но не
  меньше 1 мс: в последнюю миллисекунду окна `PTTL` отдаёт 0, а отказ обязан нести `RetryAfter > 0`.
- Длительности округляются вверх до целых миллисекунд, минимум 1 мс (`ceilMillis`, и в `NewBan`):
  `Milliseconds()` обрезает, и окно < 1 мс дало бы `PEXPIRE 0` (ключ удаляется — лимит выключен),
  а бан < 1 мс — `SET … PX 0` (ошибка уже *после* `INCR`: Redis не откатывает скрипт).
- Отклонённые запросы тоже увеличивают счётчик — для фиксированного окна это ничего не меняет.
- **Минус фиксированного окна:** на стыке двух окон проходит до 2×limit запросов (60 в конце минуты +
  60 в начале следующей). Цена простоты (`INCR` + `PEXPIRE` по контракту) — в выводы.

### Бан (`internal/ratelimit/ban.go`)

- `NewBan(rdb, limit, window, ttl)` → `*Ban`; ключи `rl:req:{key}` и `ban:{key}`, ключ — ID
  пользователя. Оба ключа в `KEYS` одного Lua `banScript`: проверка бана, `INCR` и установка бана
  атомарны.
- Порядок: бан есть → отказ, `RetryAfter` = `PTTL` бана, счётчик не трогаем. Иначе `INCR` (+TTL
  окна, если нет). `n > limit` → это действие уже отклоняется, `SET ban 1 PX ttl`, счётчик `DEL`.
- Счётчик сбрасывается при бане: иначе при `BAN_TTL < BAN_WINDOW` старый счётчик переживёт бан, и
  первая же заявка после разбана снова банит.
- Бан без TTL «лечится» так же, как счётчик (`PEXPIRE` на `ttl`). `PTTL == 0` (истекает прямо
  сейчас) считаем «бана нет» — у `Decision` при отказе `RetryAfter > 0`.

### Middleware лимита (`internal/httpx/ratelimit_mw.go`)

- `RateLimit(l, key)` → `func(http.Handler) http.Handler`; в main
  `httpx.RateLimit(apiLimit, httpx.ClientIP)(mux)` — оборачивает **весь** mux, поэтому сам
  пропускает пути не с `/api/` (статика UI не считается; `/api` и `/apix` — тоже не API).
- `X-RateLimit-Limit` и `X-RateLimit-Remaining` ставятся на любой ответ с решением лимитера, в том
  числе на 429 (`Remaining: 0`). Отказ — `WriteError(&ratelimit.LimitedError{RetryAfter})` → 429
  `rate_limited`, `Retry-After` в секундах с округлением вверх.
- Ошибка лимитера → запрос пропускается без заголовков лимита (fail-open). В лог — не чаще раза в
  10 с (`throttledWarn`, с числом пропущенных записей): иначе при отказе Redis под нагрузкой —
  тысячи строк в секунду. Если клиент уже ушёл (`r.Context().Err() != nil`), в лог не пишем — это
  не отказ хранилища.
- `ClientIP` — только `net.SplitHostPort(r.RemoteAddr)`, `X-Forwarded-For` не читаем (подделывается).
  Без порта — `RemoteAddr` как есть. За обратным прокси все клиенты получили бы IP прокси — у нас
  прокси нет. Нагрузочный тест с одной машины — один IP, один счётчик.
- Лимит стоит снаружи всего, до авторизации: флуд без токена тоже режется.
- Проверено вживую (HTTP-сервер + живой Redis, лимит 3): 200/200/200 с `remaining` 2/1/0, затем 429
  с `Retry-After: 10`, `/` без заголовков лимита.

### Общее для лимитеров

- Ошибка Redis → `(Decision{}, err)`; fail-open (пропустить и записать в лог) делает вызывающий:
  наш middleware и `requestapi` у Б — так в контракте.
- Тест атомарности `allowConcurrently`: 100 параллельных `Allow` при лимите 10 → ровно 10.
  Проверено, что тест ловит гонку: наивный лимитер `GET` → `INCR` на том же тесте пропускал 72–100
  из 100.
- Тесты проверены мутациями — каждая поломка роняет свой тест: безусловный `PEXPIRE` счётчика бана
  (окно сдвигается), «лечение» TTL через `n == 1`, отказ без нижней границы `RetryAfter`, конструкторы
  без `ceilMillis`, лог без троттлинга, лог при ушедшем клиенте.
- Живой Redis (смоук): 200 параллельных при лимите 60 → ровно 60, `RetryAfter` ≈ 60 с; бан 100
  параллельных при лимите 5 → ровно 5, бан на 15 мин, счётчика после бана нет.
- `monitor` показал «холодный старт» скриптов: при первой пачке параллельных запросов Redis ещё не
  знает скрипт, все `EVALSHA` получают `NOSCRIPT` и go-redis каждый раз повторяет через `EVAL`
  (полный текст): 301 `EVALSHA` и 254 `EVAL` на 301 вызов. На корректность не влияет (`NOSCRIPT`
  ничего не выполняет, двойного счёта нет), дальше идёт только `EVALSHA`. После рестарта Redis кэш
  скриптов пустой — повторится. Для исследования рестартов — знать.

### Наш код — исправлено
Проверка позиций в `Save`, тесты ошибок Redis и битых данных, `removeItemScript`, doc-комментарии,
`go mod tidy`, порт Redis на `127.0.0.1` — см. разделы выше.

### На следующие шаги
- **`cartapi`:** `httpx.DecodeJSON` заворачивает ошибку через `%v`, поэтому плохая дата в JSON-поле
  типа `service.Date` даёт 400 `bad_request`, а не `invalid_date`. В DTO брать `Date string` и
  вызывать `service.ParseDate` после `DecodeJSON`.
- **TTL кэша (`CACHE_TTL=60s`, дефолт из контракта, не замерялся).** TTL нужен и при явной
  инвалидации (`DEL` на `Save`/`Approve`): страхует от гонки «промах → запись старого», от упавшего
  `DEL`, от правок в обход приложения; без TTL ключ не вытесняется под `volatile-lru`, а
  `cache:schedule:{date}` копились бы. 60 с: попаданий уже ~99,9% (1 запрос в БД на ключ в минуту),
  а устаревший кэш ломает только UX — двойную бронь всё равно отсекает PK `bookings` при `Approve`.
  Услугам можно дольше, но раздельный TTL — правка `config.go` (общая зона). Вариант для
  исследования: прогнать нагрузку с разным `CACHE_TTL`, сравнить hit rate и запросы в Postgres.
- **Кэш расписания:** кэшировать и пустые дни (`[]`), иначе свободные дни всегда промах. Отличать
  `redis.Nil` от закэшированного пустого списка (nil-срез сериализуется в `null`). `DEL` — только
  после успешного `Approve`. Гонка «промах → чтение БД → Approve+DEL → устаревший SET» ограничена
  `CACHE_TTL` — описать в исследовании, не чинить.

### Исследование
- Перед замерами очистить Redis (`make flush` или `docker compose down -v`): в volume лежат ключи
  старой схемы (`request:*`, `service:*`, `services:index`, `requests:*`) без TTL — под
  `volatile-lru` они не вытесняются и портят картину.
- «Рестарт без AOF»: `docker stop` — это штатный `SHUTDOWN`, при `save 60 100` Redis пишет RDB и всё
  восстановится. Отдельно гонять с `docker kill` (SIGKILL).
- TTL хранится как абсолютное время истечения — простой съедает TTL.
- `make keys` делает 2 `docker exec` на ключ — на 64 МБ непригоден; смотреть `INFO keyspace`,
  `INFO stats` (`evicted_keys`, `expired_keys`).
- Слишком маленький `CART_TTL` (< 1 мс) превращает `PEXPIRE` в `PEXPIRE 0` — корзина удаляется.
